# 必要提问与决策记录

在需求整理后、布局前判断；后续发现新的业务冲突时也适用。提问是澄清需求，不是每一步重新索取执行授权。

先读 guided-intake.md：先查能读到的答案；用户需要方案帮助时给出有理由的推荐再问，已有完整依据则直接做。问题只服务当前范围，不把模型字段逐一问遍。目标 RP/安装依赖等属于执行环境，不因其缺失阻塞已经授权且可完成的需求理解或本地预览。明确的虚构演示按该参考中的 assumption 路线处理，不假造用户逐条确认。

## 何时必须问

先查本轮输入、已确认答复和有效基线。只有信息仍缺失且不同答案会实质改变输出时才问：
- 范围：只做 Home，还是连同下一流程；“全部”指哪些已指定页面。
- 基线：同名或多版本资料冲突，无法确定当前产品/平台的有效版本。
- 行为：按钮目的地、成功判定、保存/取消、删除影响、数据归属或跨页同步冲突。
- 权益、费用、权限等会改变用户后果的规则没有依据。
- 忠实复刻要求下，指定模板无法读取或无法知道用哪个，不能假装已经复用。
- 写入时目标 RP 不明确、版本不支持、存在外部修改或结果未知。

不要为了问而问：已回答的信息不再问；普通间距、低风险示例名可自行决定并记录。不要照单询问所有异常状态，也不要为局部页面索要完整商业方案。

## 怎么问

先识别具体条目，再分清问题类型：业务选择、技术可行性、视觉表达。标题写“需求”不能将里面的“能否实现、需讨论、正文占位”全部升级为已确认；也不能只匹配问号就认定未决，因为相邻内容可能已给出预研结论。保留依据和状态，检查现有回答是否已解决。

读取到材料中的 @某人 只表示原稿的负责人或沟通对象，不授权向其发送消息。不相关的预研问题不打断本次页面；会影响本次页面结构、流程或真实结果的未决能力才提问。回答要更新受影响规则、跨页引用和说明，不只是改 questions.status。

每轮优先 1–3 个最有影响、能一起回答的问题。每个问题交代：
1. 已知依据与具体缺口；
2. 一个清晰问题；
3. 必要时给 2–3 个合理选项及推荐理由，说明对画板/行为的影响。

例如：“目前只确定点击 Print Document 进入文件选择，但未连接时的处理没有说明。未连接时允许先选文件，还是必须先连接？这会影响 Home 按钮是否可用及右侧说明。”

推荐不等于决定。用户未回复、只说“继续”、选项被预选，都不能自动当作业务答案。明确授权低风险自主决定时可记录为 assumption；关键后果仍不能伪装成 confirmed。

## 如何继续

- 用项目 requirements-model.json 的 questions 记录 id、问题、why、blocking、affectedRequirementIds、status，以及实际 answer/answerSourceId。
- answered 必须有实际用户答复或已读取有效基线的来源，answer 与被影响规则一起更新。禁止给自己编造一条用户答复。
- deferred 必须记录 reason；不等于 answered，不解除关联规则的限制。
- 无关内容可以继续做。部分交付在 page-plan 中明确 delivery=partial、includedRequirementIds 和 omissionReason，不把暂未处理宣称为完整。
- 未解决的 blocking 问题影响当前计划时，禁止正式 preview/apply。可先整理上游文件，或仅为不受影响内容建立明确的 partial 计划。
- 全局范围/基线不明的问题 affectedRequirementIds=[]，会阻止所有 scene 输出；先问清。
- 涉及实际目标文件的操作阻塞，在连接环节解决，不能用业务问答标记绕过写入保护。

## 回答后的收口

保留问题和原答复，不删历史来伪造“从无疑问”。同步需求、表达映射、scene 和关联说明；已有 key 保持稳定。若仍有局部冲突，只追问尚未解决的部分。

简单文字答复不强制创建 JSON 文件；制作/修改原型时才走结构化文件。提问是否必要的判断由 Agent 负责，程序只能检查已经记录的问题。
