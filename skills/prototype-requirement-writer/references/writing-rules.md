# 原型与中文说明写作规则

本规则用于新建或修改需求原型。继承的是可评审、可执行的表达方式，不是示例产品的功能清单。正文以中文说明行为，App 内保留必要英文 UI 文案。

## 1. 先选交付形态

| 用户任务 | 交付组织 | 不应自动添加 |
| --- | --- | --- |
| 一页 / 一个组件 | 该页主画板、必要状态、对应说明 | 版本表、全局流程、订阅或整款 App |
| 完整新品 | 有依据的项目概览、功能页面和核心流程；页面较多时加目录或框架 | 未确认竞品、空预研页、占位迭代规划 |
| 局部迭代 | 版本/变更摘要、旧→新、受影响页面、沿用范围 | 重写所有旧页面 |
| Bugfix | 复现入口、实际行为、期望行为、影响分支、回归点 | 顺便重做视觉或商业策略 |
| 复用其他产品/平台 | 指明复用对象及版本，列差异和待验证能力 | 自动继承权限、支付、后台行为 |
| 只写说明 | 对应页面/模块的完整说明 | HTML、Axure 启动或其他外部写入 |

未填写的模板、竞品截图、预研提问与正式需求不能混为一谈；按 [参考资料甄别](source-review.md) 处理。

## 2. 页面、画板、模块分别组织

1、页面树按功能组织，例如 Home、Reader、History。Home 的空态、加载态、筛选态不是多个独立 Home 页面。
2、同一功能需要视觉比较时，在一个功能页中放多个静态画板，标题写明状态或入口。仅文案/数值变化可用映射表，不复制整屏。
3、独立任务、独立导航目的地或用户明确要求时才新建功能页。由判断条件分支出的弹窗可就近放在触发画板旁边。
4、多来源进入共用页面时，先写共同逻辑，再列来源差异；不要按文件格式或入口机械复制整套说明。
5、流程图说明先后顺序与条件；功能框架说明包含关系；全局画板只用于总览。它们不能代替详细页面规则。
6、默认只画静态状态。箭头、展开后的弹窗、拖动后的结果用于说明，不代表已制作可执行动态面板。

## 3. 画板与标注配对

1、使用“画板标题 → 页面效果 → 紧邻右侧说明”作为一个评审单元。多个单元可横排或纵排，说明跟随对应单元，不全部堆到整个大画布的最右端。
2、同一组屏幕共享规则时，允许“一组状态图＋一组说明”，但每条差异写明适用状态。
3、截图中的标题、页面内的英文导航标题、右侧说明标题分开：前者服务评审，后者才是 App UI。
4、先看用户当前指定模板的尺寸、间距、字号和控件。没有模板时，移动端单屏可从 360–390px 宽起步；这是起点，不是跨项目强制规格。不要缩小字号来塞长文。
5、已有编号保持不变；新内容按该功能页使用稳定编号，画面热点与说明一致。项目内部可用 Home.S01.R03 等追踪标识；不要求用户输入 key，也不把工程 key 当作 UI 文案。
6、蓝色编号/热点用于定位，红色可用于美术交付或明确变更，深色说明块可用于全局规则。颜色必须有文字含义，不把每段都涂成重点。
7、保留白底、简单描边、清晰选中/不可用状态；图片、图标、图表可用明确占位。不要把低保真做成营销 landing page。
8、按 [页面数据与执行](scene-and-execution.md) 使用 notes 独立坐标排版。标题、正文、编号和美术备注均需要可读；长说明分语义组或列，不截断、不强拆功能页。

## 4. 说明围绕模块展开，不机械填六个标题

一页先用简短“页面说明”讲清用途和边界；其后按实际模块展开。可采用“页面进入、顶部栏、文件列表、底部操作、页面状态、交互说明、异常&边界处理”等标题，但只保留有内容的部分。

段落用 1、2、3、编号，每条写一个完整可判断的行为。同一条规则可以紧接条件分支；不要用多层圆点堆成长树。画面已有按钮、tab、菜单项均有明确结果；纯展示元素说明“仅展示”即可。

优先写完整的行为单元：

> 在什么入口或条件下 → 哪个用户动作/事件 → 页面或数据如何改变 → 成功、取消、失败分别去哪里 → 什么状态保留或恢复。

不是每个按钮都需六段；只补对该动作有实际影响且有依据的分支。上述完整行为单元是检查维度，不是推断授权：缺少影响本次输出的业务规则时按 clarification.md 提问，不能用常见产品做法填成已确认事实。按 page-expression.md 把需求关联到控件和说明后再写 scene。

差例：“支持排序和收藏。”
良例：“点击 Apply Sort 后应用本次选择；关闭弹窗则放弃未应用选择，列表顺序保持不变。收藏成功后同步更新 Favorite，保留当前分类。”

## 5. 保存、状态和数据的闭环

1、区分进入默认值、临时编辑值和已保存值。选择、预览、Apply、Done、返回、Discard 分别是否提交要明确，不能一处说立即生效、另一处说取消恢复却没定义。
2、区分 App 功能开关、当前任务开关、临时暂停和本次提醒停止。停止提醒不自动等于关闭长期功能；具体语义取自当前需求。
3、状态至少分清“权限不可用 / 尚未操作 / 操作中 / 操作结束无结果 / 筛选无匹配 / 有缓存但已过期”。仅将真正不同的视觉状态画出来。
4、记录何时创建、什么时候才算成功、失败/取消是否留下记录；成功提示、历史新增、次数扣减必须指向同一个已确认事件。
5、明确数据归属：原文件、任务副本、历史快照、收藏引用、当前页面、某条记录、某个图层。删除历史不默认删除原文件；清空本地不默认删除外部数据。
6、返回和外部入口携带的数据不能丢：文件、设备、记录 ID、页码/工作表、筛选、来源页。中途经过权限或付费流程后，成功回原任务，取消保留已确认需保留的内容。
7、用户有实际修改或删除时，列出受影响界面和派生数据。例如详情修改后 Home/Recent/Favorite 同步；删除测量后相关趋势重新计算。不要新增不存在的消费者。
8、按钮不可用说明原因和恢复条件。失败给可执行结果；“重试”需说明重试当前任务还是重新开始，防止重复生成文件、记录或扣次。

## 6. 文案与美术交付

1、已确认原文逐字保留，包括数字、标点、换行和 UI 标签；发现问题另列建议。新增说明不能被自动“润色”成另一份规则。
2、原稿只是参考时，可迁移表达结构，不复制另一个产品的名称、价格、广告位、权限、指标或示例数据。
3、动态文案写出字段含义、格式、单复数、缺失值和示例；示例不等于固定值。价格、日期、次数不能只画一个数字不写来源。
4、美术备注放在 App 画框外。写清画板/模块、需要表达的含义、状态或动效、复用/新增范围；不只写“美术自行设计”。
5、“需要美术出图 × N”要说明口径：独立页面稿、状态稿还是插画资源。多个状态不一定等于多个独立资源；系统界面标注“系统页面，仅供参考，无需重新出图”。
6、简单动效用文字写触发、持续/循环、停止和重入规则。没有实现动效时，不在交付中称其已实现。
7、文案池每条是可单独展示的完整句子；明确命中条件、优先级、兜底和切换/重置规则。不要交付碎片拼接或一屏多个互相冲突的结论。

## 7. 根据任务风险按需深化

出现相关内容才读取 [专项规则](conditional-rules.md) 中对应章节：

- 启动、权限、外部分享、系统能力 → 入口与平台边界。
- 多格式文件、设备列表、测量和趋势 → 数据身份与统计。
- 订阅、广告、免费机会、推送 → 触发与计数。
- 预设问答/AI 洞察、健康或能力宣称 → 内容规则与证据。

这些是需要问清或写清的维度，不是让每份原型新增所有模块。

## 8. 交付前检查

1、请求中的页面/模块全部覆盖，无擅自扩展；所有不确定的关键逻辑有明确标识。
2、画面、说明、流程图、配置表中的按钮名称、入口、条件、默认值、计数、保存时机一致。
3、一组图对应一组说明，热点编号不串线；常规、选中、不可用和必要状态可辨认。
4、没有未解释的“同上”、占位正文、复制错产品/平台、无来源的价格/阈值/权限结论。
5、真实源文案与生成的 HTML/Markdown/Axure 对照；图中嵌入文字未读取时明确报告，不能只凭字符串表宣称全部核对。
6、原型可视检查包含中文、长英文、标题折行、右侧说明底部、遮罩和弹窗层级。程序校验不能代替看图。
7、核对关键行为的成功/取消/失败，数据保留与返回路径；不编造未具备的系统回调来让流程看似闭环。
8、交付注明实际完成项、待确认项及写入边界。独立产品规则建议与忠实还原的原稿分开，不偷偷改源文件。
