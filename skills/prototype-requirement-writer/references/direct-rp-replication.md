# 实际 RP 页面直接复刻

本规则只在用户明确要求复刻已提供 RP、照原稿生成，或让 Agent 从授权 RP 中自动找到最合适页面时启用。目标不是从原稿“获得灵感”，而是把真实页面作为当前产物的结构基线，同时只替换当前需求明确变化的内容。

## 1. 先选真实页面，不先画通用模板

按以下顺序逐个功能页选择：

1. 同产品、同平台、同功能页的当前有效 RP 页面；
2. 同产品、同平台、相邻版本中未被新版本覆盖的页面；
3. 同产品族、同平台、同任务页面；
4. 不同产品但同页面类型的页面，只复刻布局与控件组织；
5. 都没有时才回退到包内模式库，并明确标记 `fallback-pattern`。

必须读取候选 RP 的页面树、目标页控件和原生渲染。产品框架、思维导图、流程图、竞品截图、版本信息和研究页只能作为需求或流程证据，不能充当 App UI 页面。用户没有要求时，不生成 Product Overview、Product Scope、流程总结或设计说明首页。

## 2. 复刻的五个维度

每页在 `reference-selection.md` 与 `page-plan.json.referenceSelections` 中记录并验收：

- `layout-topology`：画板数量、横纵排列、页面框与说明列的相对位置；
- `module-density`：模块数量、信息层级、留白和页面总体长度；
- `state-boards`：原稿用几张静态画板表达哪些状态，不机械拆成新页面；
- `control-composition`：标题栏、列表、图片、Tab、弹窗、按钮、广告位、系统页示意等组合；
- `requirement-structure`：蓝色编号、业务标题、条目层级、分支缩进、美术标注及说明颗粒度。

至少四项应与真实源页面直接对应。当前需求确实改变某一项时，记录变更原因和替换范围；不能以“更简洁”“低保真”或“避免猜测”为由主动删减原稿模块。

## 3. 内容替换边界

- 当前输入与源 RP 同产品且没有冲突时，可保留原页面的业务模块、英文 UI 文案和中文说明，再按当前变更做最小修改。
- 当前输入覆盖旧规则时，只替换对应控件和说明条目，不重写整页。
- 跨产品参考时，只保留结构、密度、状态和控件组合；产品名、价格、权益、权限理由、广告频率、成功判定、数据口径和专属流程必须重新取自当前来源。
- 未确认的高后果规则按 clarification.md 提问；不能因为源 RP 有值就自动继承。
- 业务控件保持独立可编辑；不得把整页截图作为 Axure 页面交付。原生渲染图只用于选型和视觉验收。

## 4. Axure 交付策略

若同产品 RP 已包含大部分目标页面，优先把该 RP 的副本作为一次性工作基线，再通过 MCP 在同一文件中持续修改；这样可保留原控件、图片资源、富文本、页面组织和用户习惯。不要每轮新建 RP，也不要把源 RP 本身覆盖掉。

若目标页分散在多个 RP，逐页记录来源。当前桥接不能安全跨文档克隆完整页面时，先按源页原生渲染与控件树重建并做视觉对照；不得把“重新画了相似卡片”称为直接复刻。缺少可编辑复刻能力时，应明确报告该页仍处于预览/重建状态。

## 5. 交付门槛

逐页检查：

1. 主参考是否是实际 RP 页面，而不是功能图或模式名；
2. 源页面名/ID、读取结果和原生渲染证据是否存在；
3. 五个复刻维度是否至少四项可对应；
4. 源页面的主要模块、状态和说明块是否没有被无理由压缩；
5. 当前需求的变化是否只影响声明范围；
6. 页面是否仍由独立可编辑控件组成；
7. 未经要求是否完全没有 Product Overview 等总结页。

任一关键页面只使用通用卡片、占位插画和 2–3 条摘要说明时，不得交付为“已复刻”。
