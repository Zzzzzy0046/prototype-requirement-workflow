# 输入归一化与内部提示词

用户可以只说“做一个 Document Reader 的主页，有最近文件和扫描入口，右侧写中文说明，放进 Axure”。也可以提供 PRD、HTML、图片或现有模板。这些都是有效输入，不强制用户使用模板；这里的产品仅是输入示例，不提供默认页面结构。

Agent 先按 guided-intake.md 判断这轮是方案探索、按稿执行、定点修改还是虚构示例。下表是内部核对维度，不是用户必填项；先读范围内资料，再对影响当前输出的关键缺口提问。明确任务不强加方案确认，模糊任务先给简短推荐。达到可画条件后按 page-expression.md 整理 requirements-model.json 和 page-plan.json，按 clarification.md 记录问题。简要结论进入 scene.brief 及 scene.assumptions / outOfScope；完整来源和问题不能只压缩成一句 brief。

制作页面时同时按 reference-library-routing.md 选择同类参考。参考选择是 Agent 的内部准备，不要求用户先提供专业模板：若项目已有参考根目录，先读取最接近的同产品族/同平台/同页面类型页面；若没有，明确使用 fallback。参考用于补足信息角色和页面密度，新增业务模块仍按 confirmed / assumption / unresolved 区分。

正式新品或竞品对标任务改用 framework-screenshot-workflow.md：用户至少提供产品/功能名、平台、本轮范围、产品功能框架和一组手动上传的竞品截图，并说明是否允许补框架外低风险辅助模块。功能框架只决定功能范围和页面分布；竞品截图必须先抽象为低保真布局、模块、控件和状态，不能作为当前业务规则来源。没有框架或截图时只能按规则交付范围受限方案或取得 fallback 授权，不能假装输入完整。

| 内容 | 处理方式 |
| --- | --- |
| 产品、页面/流程范围 | 用户本轮明确要求优先；不扩大成整款 App |
| 使用人群、任务 | 只写依据明确的信息；缺失的低风险假设标明 |
| 平台、UI 语言、说明语言 | 用户要求优先，否则移动端低保真、海外英文 UI、中文说明 |
| 参考资料、定稿文案 | 逐份查看；区分参考布局与要求逐字保留的原稿 |
| 交付形态与基线 | 新品/局部页面/迭代/Bugfix；明确产品、平台、有效版本及继承范围 |
| 证据状态 | 已确认、历史参考、待预研、占位、未读取或冲突；不能统一当成正式要求 |
| 页面、模块、按钮结果 | 分配稳定 key，串联具体行为 |
| 状态与边界 | 挑实际相关项；不机械列全状态 |
| 目标 RP、输出目录 | 来自项目配置或用户提供的绝对路径；不得猜测 |
| 不做内容、待确认项 | 明确记录；不将假设写成事实 |

将上面内容代入以下稳定任务指令。这是 skill 内部操作，不需要用户复制：

> 根据本次交付形态、用户已确认需求和实际读取材料，为指定产品/平台/版本制作可评审低保真页面与中文说明。先区分有效基线、迭代差异、参考、预研和占位，不能混用历史规则。按功能页分别选择最接近的主参考，记录实际读取范围、借用内容和禁止继承内容；不能只写“参考过”却不影响页面层级、密度、状态、控件或说明。参考只用于信息架构、模块密度、状态表达、视觉层级、控件模式和说明颗粒度，不复制另一个产品的文案、价格、权限、广告、成功判定、数据口径或专属流程。保留定稿文案和必要英文 UI 标签；每个功能页面保持身份，必要状态用同页静态画板表达，每组图紧邻对应说明并保持编号。“只做 Home/一页”只限制页面树，不等于最小骨架。低风险参考推导作为 assumption 披露；权限、系统交接、数据写入/删除、成功判定和商业化等高后果缺口先提 1–3 个问题。一句话要求完整产品时，不允许用大量 assumption 冒充完整需求。说明目录同时允许页面生命周期标题和业务对象标题；正文按入口、触发、结果、取消/返回、失败、持久化、再次进入、系统边界和数据影响写到可判断。页面控件按 control-pattern-library.md 组合为可编辑的图片、列表、选择、弹层、系统界面和反馈模式，不因底层原子形状有限而退化成空矩形。跨页面的数据与计数保持一致。迭代写明旧→新、影响范围和沿用部分。将布局与文案放进同一份 scene.json，统一生成 HTML、说明和 Axure 控件。完成语义、参考使用、需求深度、控件表达、可视检查及 Axure 回读，再报告真实结果。继续修改沿用 key、映射和目标 RP，不重建项目，不添加未要求的商业化模块或复杂交互。

framework-screenshot 在上述稳定指令前增加：先用产品功能框架生成页面清单，用竞品截图生成页面表达抽象；用户确认页面清单后只生成 page-design，不输出完整说明。用户再次确认页面画面后才进入 final，依据框架、当前需求和已确认页面生成说明。竞品截图不能为当前产品补业务事实。

将以上稳定指令用于三段内部处理：先提取有来源的事实和缺口；再按必要提问规则收口并规划每条需求的表达去处；最后套用选定模板生成 scene。不得省略中间决策，直接从自然语言猜坐标。

已有原稿说明时，notes.lines 使用原文行，并在模型 exactCopies 记录对应目标，不经过第二轮“润色”。新增说明先生成当前页面的说明目录；页面级的 `页面说明/页面进入/展示规则/交互说明/边界&异常处理` 与业务对象标题可混合使用，不强制六段，也不能把必要生命周期规则删掉。新写说明使用 `1、2、3、`，条件分支可在主条目下缩进圆点；不强制重编已有定稿编号。同一段文字在 HTML、Markdown 和 Axure 都由此字段直接输出。version 2 只使用 schema 已定义的 context、criticality/category/visualChange、referenceSelections、pageType/stateType、componentRole 和 coverage 字段，不添加自造字段。

“通用”指可用于不同产品需求。Printer、Reader、Heart Rate、Find Phone 等都只可作为演示或来源案例；任何一个都不能成为默认业务模板。
