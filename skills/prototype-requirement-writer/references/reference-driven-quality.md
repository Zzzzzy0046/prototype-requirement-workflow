# 参考驱动的需求说明质量标准

本标准用于把用户提供的 RP、截图、PRD 或历史原型真正转化为当前页面的写法，而不是只记录“参考过”。它约束需求说明的来源、颗粒度和验收方式；不携带任何原产品的业务值。

## 1. 参考必须影响实际产出

每个功能页都要在 `reference-selection.md` 和 `page-plan.json.referenceSelections` 中记录一个主参考。主参考可以是当前有效 RP、用户本轮截图、包内 RP 派生模式或已读取的外部案例；只存在但未读取的文件不算参考。

主参考至少要实际影响以下一项：

- 页面信息层级；
- 模块密度；
- 状态画板选择；
- 控件组合方式；
- 右侧需求说明结构与颗粒度。

每页同时写明禁止继承的业务内容。若最终页面与参考在上述五项中均无可说明的对应关系，视为没有实际使用参考，不能交付。

当任务为 `direct-rp-replica` 时，要求更高：布局拓扑、模块密度、状态画板、控件组合、右侧说明结构五项中至少四项必须能逐项对应真实源页面；未对应项必须写出当前需求导致的具体理由。仅保留 360px 手机框、蓝色编号或标题样式，不算复刻。

参考优先级：当前明确需求 → 当前有效基线 → 用户提供的同类 RP/截图 → 内置 RP 派生模式 → 其他授权参考。Agent 经验只用于发现缺口、提出低风险方案或必要问题，不能越过前四层直接形成已确认业务规则。

## 2. 需求说明采用“双轴组织”

用户原稿中存在两种都有效的标题方式，不能只保留其中一种：

1. 页面生命周期标题：`页面说明`、`页面进入`、`弹窗展示规则`、`交互说明`、`边界&异常处理`。
2. 业务对象标题：例如“最近文件”“设备扫描”“测量结果”“排序与删除”。

生成时按页面复杂度组合：

- 页面只有一个主要对象时，可用生命周期标题完整展开。
- 页面包含多个独立业务模块时，使用业务对象标题，并在正文中覆盖进入、操作、结果和边界。
- 弹窗、权限、系统交接、首启流程优先保留“展示规则 / 交互说明 / 边界&异常处理”等页面级标题，因为它们比泛化的业务名更能表达触发与回流。
- 不能为了避免固定模板而删除页面进入、取消返回、再次展示或异常恢复；也不能为了套齐模板而新增不存在的业务。

## 3. 一个可执行行为单元的写法

每个关键行为先拆成以下事实，再合并成可读的 1、2、3 条：

`入口或前置条件 → 用户动作/系统事件 → 页面或数据变化 → 成功结果 → 取消/返回 → 失败 → 状态保留与再次进入`

要求：

- 一条只写一个可判断的规则，不用“支持、处理、进入下一步”等概括词代替结果。
- 有条件分支时，先写主规则，再用缩进圆点列分支；每个分支必须有落点。
- 页面内出现的按钮、Tab、菜单、开关和可点击条目都要有结果；纯展示元素明确“仅展示”。
- 跳到系统设置、系统选择器或其他 App 时，写清返回后重新读取什么状态，以及未完成时回到哪里。
- 保存、删除、授权、购买、计数、记录生成等会改变用户后果的行为，必须写明真正完成事件和失败时是否留下数据。
- 下游页面不在本轮范围时写“进入对应流程，本轮不展开”，不能虚构下游成功逻辑。

## 4. 页面说明覆盖检查

以下是检查维度，不是固定章节。每个页面只选择适用项，但不得跳过实际存在的规则：

| 维度 | 要回答的问题 |
| --- | --- |
| purpose | 页面/弹窗解决什么问题，适用于什么对象和范围 |
| entry | 从哪里、在什么条件或用户状态下进入/展示 |
| display | 当前状态展示哪些字段、控件、默认值和动态内容 |
| trigger | 用户动作或系统事件是什么 |
| result | 页面、导航、数据或系统状态如何改变 |
| cancel-return | 返回、关闭、取消、跳过时落到哪里，临时值如何处理 |
| failure | 失败、超时、无权限、无数据时给什么可执行结果 |
| persistence | 哪些值即时保存、提交后保存、仅本次有效或不保存 |
| reentry | 再次进入、回前台或系统返回时是否再次展示和怎样恢复 |
| system-boundary | App 页面、系统页面、外部 App 和真实系统状态如何区分 |
| data-impact | 创建、更新、删除会影响哪些真实对象和已知消费者 |
| art-delivery | 哪些图片、图标、状态稿或动效需要新增/复用，数量口径是什么 |

scene version 2 的每个 note 使用 `coverage.requirementIds` 与 `coverage.aspects` 声明实际覆盖项。声明必须能从正文中读出来；不能只加 metadata 骗过校验。

## 5. 必要提问与 assumption 门槛

以下内容不能由参考或产品常识直接定稿：页面范围、主任务选择、权限是否阻塞、成功判定、保存时机、删除范围、数据归属、支付/广告、系统返回、跨页同步和高风险能力。

- `criticality=high` 的需求不得标记为 assumption；缺少来源时改为 unresolved 并提出必要问题。
- 一句话要求“完整产品”且输入为 minimal/partial 时，若超过一半已纳入需求依靠 assumption，并且 assumption 不少于 4 条，完整计划必须被阻止。应先提 1–3 个方向性问题，或明确交付为范围受限的方案提案。
- 用户明确要求虚构示例时可用 `decisionMode=explicit-fiction`，但仍需披露假设，不能伪造用户确认。
- 低风险视觉层级、占位内容和标准控件可作为 assumption；价格、权限后果、删除、数据写入和系统能力不能。

## 6. 状态是画面还是文字

当状态改变页面结构、可用操作、用户决策或系统上下文时，使用 `visualChange=true` 并生成独立静态画板。例如权限拒绝恢复、确认删除、文件冲突、处理中失败、空态与有内容状态、系统弹窗或 Bottom Sheet。

只有文案、数值或轻微提示变化时可写进说明。不要把每个错误都画一屏，也不要把所有关键状态都塞进右侧文字。

## 7. 交付前人工复核

程序通过后仍逐页核对：

1. 页面主参考是否真的体现在布局、密度、状态、控件或说明中。
2. 是否存在一个蓝色编号覆盖多组无关规则。
3. 关键行为是否有入口、触发、结果和必要的取消/失败/恢复。
4. 是否用“Retry、返回、保存、同步”等词，却没有说明重试对象、返回落点、保存事件或同步方向。
5. 是否将原稿的页面级说明过度压缩成 2–3 句摘要。
6. 是否把 Agent 提案写成 confirmed，或用大量 assumption 冒充完整 PRD。
7. 是否有画面关键状态没有对应说明，或说明中的关键状态没有必要的视觉表达。
8. `direct-rp-replica` 是否出现了源 RP 中不存在的 Product Overview、功能总结页、通用卡片首页或重新编写的简版说明；若用户未要求，任一出现即不通过。
