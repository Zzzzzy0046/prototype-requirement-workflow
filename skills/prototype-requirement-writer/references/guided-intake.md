# 从少量输入收敛到可画需求

这是 Agent 的判断方法，不是给用户的新表单。输入归一化字段用于内部核对，不能把每个空字段变成问题。这里判断下一步如何推进；clarification.md 定义问题记录与阻塞规则。

## 先判断这轮需要什么帮助

| 输入与上下文 | 下一步 |
| --- | --- |
| 只有想法，没有可执行方案 | 利用已有资料，提出简短推荐范围，确认最关键的业务分歧 |
| 有 PRD/有效基线，要求按稿做 | 先读资料；明确内容直接执行，只问会改变当前结果的真实缺口 |
| 已有项目的一处修改 | 定位原对象、规则和反馈；保留未涉及范围、key、样式和答案，不重做全量访谈 |
| 明确“随便做个示例/你决定，先看看” | 用标明的虚构低风险假设出样例，不冒充正式需求，不连接真实业务或账户 |

一句话不一定模糊：若项目和已有答复足以确定含义，就直接做。长 PRD 也可能有关键冲突。不得按关键词或输入长度机械分流。

正式新品或明确要求竞品对标时，按 framework-screenshot-workflow.md 收集最小输入。不要把它变成长问卷：优先让用户一次提供产品功能框架、竞品截图、平台和本轮范围。已有对话已经给出其中某项时直接复用，不重复询问。缺少框架时不能自行扩写完整页面树；缺少截图时不能声称竞品对标，只有用户接受 fallback 才能使用团队页面模式库。

## 先找答案，再提出建议

只检查用户放在本任务范围内的资料、当前项目绑定和已确认答复。制作页面时按 reference-library-routing.md 检查用户提供文件、项目 `reference-library/`、`referenceRoots` 或本机明确登记的私有目录，选择同产品族/同页面类型的主参考。优先读取明确文件/页面；没有线索就不要扫描整个电脑、接管旧 RP 或搜索无关任务。没有资料时直接说明，不能声称已经参考模板。

- 可查信息：先读现有资料，找到依据则沿用，不再索取。
- 可自行处理：普通间距、字号、说明编号、非业务示例名；按模板或已声明的低风险默认处理。没有指定模板时不把模板选择强制变成问题。
- 关键决策：页面范围、主要任务/操作、权益/费用/权限/删除/成功判定，以及冲突基线。资料不能解决时需要用户判断。

用户需要方案帮助时，给一个有理由的推荐，让用户判断而不是从零列功能。几句话即可：“目标理解 → 建议组成与边界 → 一个最有影响的问题”；不要求每轮套三个标题。建议无来源就明确为建议，不能反填 user/baseline。

例如只有“做一个扫描工具主页”：先找同类工具 Home 参考其任务层级、模块密度和状态表达，直接给出一个包含主入口、当前状态、最近结果/继续任务及必要辅助入口的低保真提案，新增模块标为 assumption。只有扫描对象、是否依赖外部设备等答案会改变主页主结构时，才问 1–3 个关键问题。不要同时追问地区、价格、字号、RP 路径、所有失败态和完整参数。产品主任务完全未知时先问主任务，不擅自替用户选产品。

“只做一页”不是“只做一个控件”。它限制页面树和下游展开范围；页面本身仍应达到可评审密度。除非用户明确要求极简骨架，或有效原稿就是极简结构，否则不能为了避免假设而删除同类参考中能支撑主任务的低风险信息角色。具体门槛见 reference-library-routing.md。

“方案探索”不等于只能问不能推进：先整理范围内已明确的内容。需要画面比较时，说明候选用途并取得相应方案确认或低风险示例授权；不能用“探索草图”绕过未决关键业务门禁，或把候选当正式需求写入 RP。

## 问到足够，不问到完美

每轮优先 1–3 个真正独立的决策。一个问题里塞十个字段仍是长问卷。答案应能改变当前画面或规则，不为证明专业而列全异常。

可执行条件：本轮对象和范围能定位；主任务和主要操作有依据；影响当前表达的关键分歧已解决；低风险表达默认可以明确说明。不是所有生命周期细节都必须先确定。

只做 Home，可写“点击后进入文件选择，本轮不展开下游”，不必先补完整条文件选择流程。下游未知若决定 Home 按钮可用性/费用/结果，仍需澄清该点。不要编造下游成功、取消或保存规则。

用户否定建议就替换被否定部分；明确接受某项建议时记录实际答复和范围。“继续”若无法判断是在授权执行还是回答业务分歧，不自动当作选择。低风险自主设计不等于确认关键业务。答复后只核对剩余依赖，不要求再确认一遍全部页面。

## 业务与环境分开

目标 RP、依赖、安装位置是执行阶段信息。业务足够而 RP 未提供时，可先在当前项目输出已授权的本地规划/预览，说明 Axure 尚未写入；实际写入前才询问目标。只要文字/HTML 时不要求 RP、不启动 Axure。

没有 runner 时仍可在范围内做需求理解和方案收敛，不伪造已运行校验，也不把安装路径作为业务引导的第一个问题。完整写入授权也不允许猜目标、覆盖外部修改或绕过真实阻塞。

## 对接现有模型，不新增用户填表

初次短对话未收敛时，可先在对话或 request.md 保存必要摘要，不为凑齐 schema 发明页面、规则和 question id。正式生成前再写完整 requirements-model/page-plan。

- 已确认内容：保留实际来源及字段来源。
- 尚待选择的关键规则：unresolved 和真实问题；不得以推荐填 confirmed。
- 获授权的虚构样例规则：assumption，标记演示用途与假设来源，statement 同步进 scene.assumptions。明确的用户请求本身可 confirmed，但“允许自主设计”不等于逐条确认了 Agent 的具体选择。
- 已有真实未决关键规则：不能用“样例”或 assumption 伪装为已解决。部分继续仍用 partial 及真实原因。

最终简要说明画了什么、哪些是建议/假设、哪些待确认、是否实际写入 Axure。内部分类、JSON 和运行协议不变成每次交付的长说明。

framework-screenshot 有两道明确确认门，不把它们合并为一句“继续”：第一次确认页面清单和参考匹配；第二次确认已经生成的页面画面。第二次确认前只修改页面，不生成完整右侧需求说明。确认必须记录用户实际答复来源，Agent 不能自行把 pending 改为 approved。
