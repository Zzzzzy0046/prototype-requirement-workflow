# 竞品截图与产品功能框架驱动的原型工作流规范

版本：2.0 草案  
适用范围：新品低保真原型、已有产品新增功能、指定页面改版，以及 Axure RP 11 原生交付。

## 1. 工作流目标

本流程把原型生成的三个问题分开处理：

1. **做什么**：由产品功能框架定义产品范围、功能层级和页面分布。
2. **怎么画**：由用户手动上传的竞品截图提供页面结构、模块密度、控件组合和状态表达参考。
3. **怎么交付和评审**：由团队 RP 模板定义画板、标题、编号、需求说明和 Axure 控件规范。

Agent 不再根据一句产品名称自由补完整产品，也不能把竞品截图中的业务规则直接当成当前产品需求。

## 2. 三类输入及其职责

### 2.1 产品功能框架：范围来源

产品功能框架是页面规划的主要依据，可以是思维导图、流程图、表格、文字树或 PRD 目录。

它负责定义：

- 产品包含哪些一级功能域；
- 每个功能域下有哪些用户任务；
- 哪些任务需要独立页面；
- 哪些内容属于同页模块、操作步骤、参数或状态；
- 页面之间的主流程和入口关系；
- 本轮要做全量、局部页面还是某条流程。

它不负责定义：

- 页面具体布局；
- 卡片、列表、Tab、Bottom Sheet 等控件样式；
- 页面视觉密度；
- 竞品特有的文案、价格、权限、广告和数据规则。

### 2.2 竞品截图：页面表达来源

竞品截图由用户手动上传。每张截图先被抽象为低保真页面模式，再参与当前产品页面设计。

竞品截图可以提供：

- 页面布局拓扑；
- 信息层级；
- 模块数量和页面密度；
- 控件组合；
- 导航方式；
- 主要操作的位置与强调关系；
- 空态、有数据、处理中、弹窗等状态的表达方式。

竞品截图不能直接提供：

- 当前产品的功能范围；
- 当前产品的业务规则；
- 价格、试用期、权益、广告频率；
- 权限后果、保存时机、删除范围；
- 成功判定、数据口径和系统能力；
- 竞品品牌、Logo、配色、图片素材和受保护文案。

### 2.3 团队 RP 模板：交付格式来源

团队 RP 模板只负责统一最终交付形式：

- 左侧页面效果、右侧对应需求说明；
- 画板外标题及 S01/S02/S03 状态编号；
- 蓝色 1/2/3 编号代表需求说明模块，不代表页面或布局行；
- 中文需求说明的标题、条目层级和密度；
- 海外产品默认英文 UI、中文需求说明；
- 控件必须独立可编辑，默认不 Group；
- 多画板保持紧凑排列，说明紧邻对应页面；
- 默认静态可评审，不依赖复杂交互和动态面板。

RP 模板不能为当前产品补充业务事实。

## 3. 最小用户输入

正式生成前至少需要以下内容：

1. 产品名称或本次功能名称；
2. 目标平台，例如 Android；
3. 产品功能框架；
4. 至少一组竞品截图；
5. 本轮范围，例如全量新品、某条流程、Home 或指定页面；
6. 是否允许在框架外补充低风险辅助模块。

可选输入：

- 指定某张截图参考哪个功能；
- 页面流程图；
- 已有 RP 基线或团队模板；
- 必须保留的英文 UI 文案；
- 目标 `.rp` 文件路径；
- 明确不做的功能或页面。

用户不需要编写 Prompt、JSON 或控件坐标。Agent 负责将自然语言、图片和文件转换为内部结构。

推荐的简短输入格式：

```text
产品：AI Room Design
平台：Android
范围：完整新品 / 只做 Home / 指定流程
功能框架：见附件
竞品截图：见附件
补充边界：不优化功能，不新增框架外业务；允许补标准导航和空态
目标 RP：可选
```

## 4. 完整工作流程

### 阶段 A：输入登记与边界识别

Agent 保存原始请求和附件清单，区分：

- 当前产品功能框架；
- 当前流程图；
- 竞品截图；
- 团队 RP 模板或已有产品基线；
- 定稿文案；
- 仅供参考、待研究或不纳入本轮的材料。

输出：

- `request.md`
- `input-manifest.json`
- `source-review.md`

若资料身份冲突，先解决冲突，不按文件名或修改时间猜测有效版本。

### 阶段 B：功能框架拆解

Agent 将功能框架转换为功能树，但不采用“一个节点就是一个页面”的机械规则。

映射规则：

| 框架节点类型 | 默认页面表达 |
| --- | --- |
| 一级稳定功能域 | 根页面、Tab 或页面组 |
| 可独立完成的用户任务 | 功能页面 |
| 连续且需要用户决策的步骤 | 流程页面 |
| 页面中的内容分区 | 页面模块 |
| 筛选、排序、参数、工具动作 | 控件、弹层或 Bottom Sheet |
| 空态、成功、失败、权限变化 | 同功能页静态状态画板或需求说明 |
| 后台能力、数据规则 | 需求说明，不单独画 App 页面 |

每个候选页面至少记录：

- 页面名称；
- 所属功能域；
- 用户目标；
- 入口；
- 页面主要任务；
- 需要承载的框架节点；
- 可能需要的状态；
- 是否在本轮范围。

输出：

- `function-model.json`
- `page-inventory.md`

### 阶段 C：竞品截图低保真抽象

Agent 逐张查看截图，不直接照搬整张图片，也不只做“看过”的记录。每张截图形成一份结构抽象：

1. 页面类型和主任务；
2. 布局拓扑；
3. 模块清单及顺序；
4. 主次信息层级；
5. 控件模式；
6. 状态与反馈方式；
7. 可借用部分；
8. 禁止继承部分。

抽象时移除：

- 品牌和视觉包装；
- 竞品专属文案与数据；
- 未经当前产品框架确认的功能；
- 商业化、权限和系统规则；
- 无法确认来源的交互结果。

输出：

- `screenshot-abstractions.json`
- 可选的低保真截图结构预览

### 阶段 D：页面与竞品参考匹配

Agent 为页面清单中的每个页面选择：

- 一个主竞品参考；
- 最多两个辅助参考；
- 没有合适截图时使用团队 RP 模式库作为 fallback。

匹配优先级：

1. 同平台、同页面类型、同主任务；
2. 同页面类型、主任务相近；
3. 同模块组合；
4. 团队已有 RP 同类页面；
5. 通用页面模式库。

每页必须写清：

- 选择了哪张截图或哪个 RP 页面；
- 借用布局、密度、控件、状态中的哪些部分；
- 哪些内容明确不继承；
- 当前功能框架导致了哪些修改。

输出：

- `reference-selection.md`
- `page-reference-matrix.json`

### 阶段 E：必要提问

Agent 先读取现有资料，再只问会改变页面范围、主流程或高后果规则的问题。每轮建议 1–3 个。

必须提问的情况：

- 功能框架无法判断本轮页面范围；
- 同一功能在框架与用户描述中冲突；
- 竞品截图与功能页面无法建立合理对应；
- 不确定某节点应独立成页还是只做页内模块，且会显著改变页面树；
- 涉及权限阻塞、系统交接、保存、删除、付费、广告、成功判定等规则；
- 全量产品中存在重要功能没有任何可用页面参考，且无法低风险表达。

不需要提问的情况：

- 字号、间距、边框和普通排版；
- 非业务占位数据；
- 标准返回、标题栏和底部导航样式；
- RP 模板已经明确规定的评审格式。

### 阶段 F：页面清单确认门

这是第一个必须存在的产品确认门。Agent 提交页面清单，不先画完整原型。

页面清单应包含：

| 页面 | 来源功能 | 页面目标 | 主要模块 | 参考截图 | 状态画板 | 本轮是否生成 |
| --- | --- | --- | --- | --- | --- | --- |

用户需要确认的是：

- 页面有没有漏；
- 页面有没有多；
- 功能分布是否正确；
- 哪些状态需要画出来；
- 参考截图是否匹配。

确认后生成 `page-plan.json`。后续若页面树变化，需要记录差异，不静默扩充。

### 阶段 G：先生成页面，不生成需求说明

Agent 根据已确认页面清单制作低保真页面。

页面生成规则：

- 功能框架决定页面和模块范围；
- 竞品截图抽象决定布局、密度和控件组合；
- 团队 RP 模板决定画板尺寸和交付样式；
- 竞品高保真视觉降级为可编辑低保真控件；
- 页面必须达到可评审密度，不得只剩标题、卡片和一个按钮；
- 页面中的核心任务、当前内容或状态、辅助入口、结果承接和必要导航必须逐项判断；
- 一个功能页可以包含多张状态画板，但不机械拆成多个页面；
- 所有 Axure 业务控件独立可编辑，默认不 Group；
- 不生成 Product Overview、功能框架展示页、竞品截图页或研究总结页，除非用户明确要求。

输出：

- `page-scene.json`
- 页面 HTML 预览
- 页面预览图
- 可选的 Axure 页面草稿

### 阶段 H：页面画面确认门

这是第二个必须存在的确认门。用户先检查：

- 页面结构是否符合功能框架；
- 是否遗漏关键模块；
- 模块密度是否接近所选竞品；
- 控件是否足够丰富且符合任务；
- 状态画板是否必要且完整；
- 页面是否符合团队 RP 风格。

页面没有确认前，不生成完整右侧需求说明，避免说明为错误页面背书。

### 阶段 I：根据已确认页面生成需求说明

需求说明以“当前功能框架 + 已确认页面 + 用户补充规则”为依据。竞品截图只能帮助确定说明颗粒度，不能提供业务结论。

生成顺序：

1. 按页面识别实际模块和可交互对象；
2. 为每个说明块确定业务标题或页面生命周期标题；
3. 将页面控件逐项映射到入口、触发和结果；
4. 补充框架中明确但页面无法直接呈现的规则；
5. 对高后果缺口提问，不用竞品行为代填；
6. 将说明紧邻对应页面或状态画板排布。

每个关键行为根据实际需要覆盖：

`入口/前置条件 → 用户动作/系统事件 → 页面或数据变化 → 成功结果 → 取消/返回 → 失败 → 状态保留与再次进入`

说明格式：

- 蓝色编号 1/2/3 对应说明模块；
- 标题优先使用实际业务模块名；
- 页面只有一个主要对象时，可使用“页面说明、页面进入、展示规则、交互说明、边界&异常处理”；
- 多业务模块页面按业务对象拆分，例如“最近项目”“风格选择”“生成入口”；
- 使用 `1、2、3、` 写可判断规则；
- 条件分支放在主条目下缩进；
- 不把 UI 文案、美术说明和产品规则混写；
- 页面按钮、Tab、菜单、开关和可点击条目必须有结果或明确“仅展示”。

输出：

- `requirements-notes.json`
- `requirements.md`

### 阶段 J：合并、写入 Axure 和验证

页面与需求说明确认后合并为同一份最终 `scene.json`，由同一数据源生成 HTML、Markdown 和 Axure。

写入规则：

- 首次写入使用用户指定的 `.rp`；
- 后续修改复用同一 RP、同一页面 key 和控件 key；
- 不为每次修改生成新 RP；
- 不使用 Computer Use、剪贴板或键鼠模拟；
- 写入后执行页面树、控件数量、文字、坐标和 Group 数量回读；
- 必须保存并查看 Axure 原生渲染图；
- HTML 正确不能替代 Axure 原生验收。

输出：

- `scene.json`
- `prototype.html`
- `requirements.md`
- 更新后的 `.rp`
- `axure-map.json`
- `verification.json`
- `output/axure-render/`

## 5. 关键数据关系

```text
产品功能框架
  └─ 决定功能树、页面清单、页面范围和页面关系

竞品截图
  └─ 抽象为布局、密度、控件和状态模式

功能页面 × 竞品模式
  └─ page-reference-matrix
       └─ 页面清单确认
            └─ 低保真页面
                 └─ 页面画面确认
                      └─ 中文需求说明
                           └─ Axure 原生写入与持续修改

团队 RP 模板
  └─ 贯穿页面画板、编号、说明排版和控件交付规范
```

## 6. 页面完整性标准

每个功能页面至少完成以下判断，不要求机械出现所有模块：

1. 页面解决的主要任务是什么；
2. 用户从哪里进入；
3. 首屏最重要的操作是什么；
4. 当前内容、状态或历史记录如何表达；
5. 是否需要搜索、筛选、排序、创建、导入等辅助入口；
6. 操作完成后页面如何承接结果；
7. 空态、有数据、处理中、失败或权限变化中哪些需要画面；
8. 页面如何返回或进入其他功能；
9. 哪些内容来自框架，哪些是低风险设计假设；
10. 哪些关键规则仍需用户确认。

“只做 Home”只限制页面树，不代表 Home 可以缺少完整信息架构。

## 7. 竞品抽象验收标准

竞品参考必须至少实际影响以下两项，才算被使用：

- 布局拓扑；
- 模块密度；
- 信息层级；
- 控件组合；
- 状态表达。

若用户要求“复刻某张截图”，至少四项应可逐项对应；无法对应的部分必须说明是由当前功能框架或平台差异造成。

禁止以“参考了竞品”为理由直接复制：

- 品牌资产；
- 完整 UI 文案；
- 专属插画；
- 价格、权益和商业化策略；
- 权限和系统能力；
- 未在当前功能框架中的新业务。

## 8. 需求说明验收标准

逐页检查：

1. 说明是否在页面确认后生成；
2. 每个蓝色编号是否对应一个实际说明模块；
3. 每个可点击控件是否有明确结果；
4. 页面进入、取消返回、失败恢复是否在需要时写清；
5. 保存、删除、权限、付费和数据变化是否有真实完成条件；
6. 是否遗漏页面中已经画出的业务模块；
7. 是否出现页面没有的虚构功能；
8. 是否把竞品规则写成当前产品规则；
9. 是否把完整需求压缩成 2–3 条泛化描述；
10. 说明的密度、编号、缩进和排版是否符合团队 RP 模板。

## 9. 全流程阻断条件

以下情况不能宣称“完整交付”：

- 没有产品功能框架，却自行生成完整页面树；
- 没有读取竞品截图，却声称按竞品设计；
- 页面清单没有经过确认就直接生成全量页面；
- 页面画面未确认就生成完整需求说明；
- 页面关键业务超过一半依赖 Agent 假设；
- 竞品截图被当成当前产品业务规则；
- 功能框架图被直接画成 Product Overview 页面；
- 页面只使用通用卡片和占位符，未体现选定参考；
- Axure 页面被整体截图代替，或控件被整体 Group；
- 只验证 HTML，没有验证 Axure 原生渲染和可编辑性。

## 10. 建议的默认执行策略

### 现在必须做

- 要求用户提供产品功能框架和竞品截图；
- 手动上传截图，不自动抓取竞品；
- 先输出页面清单；
- 页面清单确认后先画页面；
- 页面确认后再写需求说明；
- 最终持续写入同一 Axure RP。

### 可以后置

- 自动采集 Google Play、Mobbin 或其他竞品截图；
- 自动识别多套竞品方案并评分；
- 页面模式库的自动成长；
- 复杂交互和动态面板；
- 自动生成高保真视觉稿。

### 不要做

- 无输入自动扩写完整产品；
- 用功能框架决定 UI 布局；
- 用竞品截图决定产品范围；
- 先写需求说明再倒推页面；
- 每轮新建 RP；
- 将研究页、竞品页和框架页混入正式功能原型。

## 11. 一句话原则

**功能框架决定页面分布，竞品截图决定低保真页面表达，团队 RP 模板决定交付格式；先确认页面清单，再确认页面画面，最后生成需求说明并持续写入同一 Axure 文件。**
